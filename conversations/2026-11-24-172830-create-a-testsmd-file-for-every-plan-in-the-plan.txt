● I wrote a tests.md next to every plan.md, 13 files in all, covering
  00-scaffold and m01 through m12. I haven't run or checked any of the cases.
  They come from reading the plans, requirements.md and technical-spec.md, and
  they use the real sample files.

  Each case has a numbered ID (such as M7-50) with its input and expected
  result. Each file ends with a "Done when" line. Cases are tagged with your
  four edge cases:

  - [DUP] is duplicate items across meetings. It's covered most heavily in m07
    (merging, status and due-date history, items that must stay separate) and
    m09 (ingesting twice, nothing lost in merging).
  - [GAP] is a missing owner or date. It's covered in m03, m04, m06, m07, m09
    and m10, including untitled.md, Someone and TBD, and due phrases that can't
    be resolved. Those items are kept and shown, never dropped.
  - [NAME] is two people with the same first name. It's covered in m05, m07,
    m10, m11 and m12. The cases include the two Priyas and two Rahuls, the five
    known ambiguous owner cases, and an alias in the config that settles one of
    them. Ambiguous owners are refused by list --owner and followup, never
    guessed.
  - [BAD] is malformed notes. It's covered in m01, m02, m03, m08, m09 and m12.
    The cases include the empty file, the PNG saved as .md, whitespace-only
    files, broken YAML, unclosed code fences and a corrupt store file. m09 also
    has a test that sends random byte files through ingest and checks it never
    throws.

  The numbers in the cases match the plans (35 .md files scanned, 33 read, 2
  skipped, 3 ignored candidates, 5 ambiguous owners), and the m12 file ends with
  a run of acceptance criteria 1–14 through the real binary.

  - Pinned cases: Where the plans leave a behaviour open, I wrote the case as
    "pinned": the test should lock in whichever behaviour you choose. Examples
    are whether a later occurrence with no due date erases an earlier date, and
    how next Monday behaves from a Sunday.
  - README: I added one line to plans/README.md describing tests.md and the four
    tags.

  The next step is tasks.md, which can be built from these IDs.

> also do we need test cases for a cli tool?

● Yes, and they're already in the plan. m12-cli/tests.md
  (actiontrack/docs/plans/m12-cli/tests.md) has about 140 cases for the CLI.
  Because the CLI is the only thing users touch, it needs two kinds of tests
  that the core modules don't.

  What's covered in m12:
  - Help and usage: --help, unknown commands, bad flag values.
  - Exit codes: 0 for success (including skipped files), 1 for real failures.
  - stdout vs stderr: results go to stdout and errors to stderr. --json must
    emit nothing else, so scripts can parse it.
  - Output rendering: table columns, truncation, colour only on a TTY, and
    --no-color / NO_COLOR.
  - Error messages: each one says what happened and what to do (NFR-6).
  - End-to-end: spawns the built binary against a temp store and a copy of the
    fixtures, then runs acceptance criteria 1–14 (M12-130 to M12-143).

  Two gaps worth adding:
  1. State between commands. The cases cover ingest → done → ingest and followup
     twice, but not wrong command order, such as done or followup before any
     ingest. list with no store is covered (M12-50).
  2. Cross-platform and install checks. There's only one Windows case (M12-107).
     Missing are paths with spaces, running from a different working directory,
     --store as a relative path, and a smoke test of the packed tarball (npm
     pack, install, run). The npm link check in the plan is a manual step, not a
     test.

  I can add these as a short section to the m12 file if you'd like. They'd be
  small, about 10 cases.
