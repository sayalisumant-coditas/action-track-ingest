  Design choices worth checking:
  - Fake action items: a line-by-line state machine tracks fenced code and
    multi-line HTML comments, and rejects quoted lines, so the fake checkboxes
    in 09-21 and 10-09 are never stored.
  - Dates: I wrote our own resolver with the rules in a fixed order, because
    libraries guess. Anything it can't resolve stays null instead of being
    guessed.
  - De-duplication: merging uses word-set similarity with a stage-verb guard.
    That guard keeps "estimate SSO work" and "start SSO spike" as separate
    items. Borderline pairs go into the ingest report rather than being merged.
  - Stable ids: ids come from the first occurrence's content, so they don't
    change when you resolve an ambiguous owner.
  - Manual edits: done marks and owner resolutions are stored separately and
    re-applied after every ingest, so re-ingesting doesn't undo them.
  - No send path: the Gmail interface has a single createDraft method, and a
    test checks that --dry-run never calls it.
  - Gmail connector: followup runs against a file-based mock first. The real MCP
    adapter is the last milestone, because the connector needs a one-time
    sign-in that may not work from a standalone CLI.

  The spec also has an 8-milestone build order, a test strategy and a risk
  table. Each milestone has to pass its tests before the next one starts.

  Three things need your answer before I start coding. I defaulted to them, and
  the spec's section 10 lists them: the weekday rule (a due weekday that matches
  the meeting's own weekday means +7 days), where email addresses come from (a
  people.json config), and whether you can authorise the Gmail connector. I also
  assumed Fastify for the API, and that the UI and API come after the CLI
  milestones.
